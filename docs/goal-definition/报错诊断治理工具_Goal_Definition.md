# 《报错诊断治理工具》Goal Definition

## 1. 工具目标

**构建一个以报错为输入、多源数据关联分析为核心、治理决策为输出的智能诊断工具。通过对报错体验问题的识别，关联报错触发信息、客户反馈、旅程埋点数据、运营工单、客户标签、体验评估标准知识库，综合诊断出“问题是什么、影响谁、影响大不大、值不值得修、怎么修、修改预计成效如何、后续怎么验证”，并能够结合已有平台工具实现便捷修复、上线跟进、自动回检和知识沉淀。**

本工具不是替代人工决策的全自动治理系统，而是用于提升报错诊断、证据整合、治理建议生成、状态跟进和回检归档效率的**半自动决策辅助工具**。凡是涉及生产发布、研发排期、最终归因结论和正式知识库沉淀的动作，均需保留人工确认节点。

在该目标下，工具需要完成以下核心任务：

* 从报错文案和触发场景中提取关键特征，包括错误类别、业务模块、任务类型、校验逻辑、旅程节点、根因推断和检索关键词。
* 调用多源数据，包括客户反馈、优化工单、埋点数据、体验标准知识库、业务知识库、历史治理案例等，进行检索与匹配。
* 将多源检索结果进行交叉关联分析，从客户影响、旅程影响、报错规模、体验问题严重度、历史治理收益、修复可行性等维度综合识别高价值、高优先级报错问题。
* 对照体验评估标准，从时机、形式、文案、交互流程四个维度判定报错在各维度的违规情况和严重度。
* 预估优化后的成效，包括报错量下降、投诉减少、任务完成率提升、运营咨询压力下降等，并标注预估可信度。
* 判定实施路径，不再仅采用“开发路径 / 文案路径”二分法，而是显式区分纯文案发布、配置化体验、前端交互改造、后端 / 规则逻辑改造四类路径。
* 生成可执行的设计优化建议，包括交互、时机、形式、文案、帮助中心文章和验证指标。
* 在 AI 生成综合诊断报告后，支持人工复核与状态分流，将人工结论写回治理台账，并形成规则修正候选。
* 输出回检方案：有埋点条件时给出回检指标、基线窗口、观察窗口和回检周期；无埋点条件时给出埋点补齐方案。
* 在自动回检前，补充上线与回检准备登记，包括实际上线时间、上线范围、上线版本、埋点口径和埋点文档。
* 上线后自动拉取多维度数据进行回检，标记成效提升条目；对无明显成效条目进行复诊分析或延长观察周期。
* 将优化结果、复核结论、回检结果归档到知识库，包括成功案例、踩坑记录、规则修正候选，持续提升后续评估准确度。

---

## 2. 最终产物

本工具最终要交付的，是一个**从评估诊断到实施上线、从人工复核到自动回检、从结果归档到规则反哺的完整治理链路**，而不是零散的分析片段。

最终必须产出的内容包括：

### （1）完整链路范围定义

明确本工具应覆盖的环节，包括：

* 报错输入 → 字段标准化 → 特征提取
* 多源数据检索，包括客户反馈、优化工单、埋点数据、体验标准知识库、业务知识库、历史治理案例
* AI 交叉关联分析与影响评估
* 体验问题严重度判定，对照体验标准进行时机、形式、文案、交互流程多维度违规评估
* 优先级评分、成效预估与可信度判断
* 实施路径判定，区分纯文案发布、配置化体验、前端交互改造、后端 / 规则逻辑改造
* 综合诊断报告生成，包括体验问题描述、证据来源、优化方向、预计成效、回检方案
* 人工复核与状态分流，包括评估准确、暂未复现、无需优化、需补充信息、需产品确认、需研发确认、需补充埋点等结论
* 开发路径 → 设计方案效果输出 / 开发治理排期跟进
* 文案路径 → 文案发布包生成 / 文案治理平台发布，发布前必须人工确认
* 上线与回检准备登记，包括实际上线时间、上线范围、上线版本、灰度 / 全量状态、埋点文档、指标口径
* 回检就绪检查，判断是否具备自动回检条件
* 上线后自动回检数据拉取与对比
* 成效判定：有成效 → 成功案例待确认；无明显成效且样本充足 → 复诊 / 踩坑记录；无明显成效但样本不足 → 延长观察周期
* 知识库归档，包括成功案例、踩坑记录、规则修正候选、埋点缺口经验

### （2）链路分层结果

整套工具按以下六层组织：

#### 1. 评估诊断层

**范围**：报错输入 → 多源检索 → 交叉分析 → 综合诊断报告。

**解决问题**：判断报错“是什么问题、影响谁、影响大不大、是否值得治理”。

**相关治理阶段**：评估阶段。

**为什么不能缺失**：这是工具的核心判断层，决定后续是否进入治理、走什么路径、需要什么证据。

**上下游衔接**：

* 上游承接增量过滤、高频过滤、去重助手输出的待评估报错条目。
* 下游输出综合诊断报告和人工复核卡，进入运行控制层。

---

#### 2. 运行控制层

**范围**：运行状态记录 → 异常捕获 → 问题池分流 → 人工复核卡 → 人工结论回写。

**解决问题**：解决最小链路中“AI 诊断后如何被人工接管、如何记录状态、如何处理异常、如何沉淀修正规则”的问题。

**相关治理阶段**：评估阶段 / 治理跟进阶段。

**为什么不能缺失**：如果只有 AI 报告，没有复核与状态流转，工具无法真正进入治理流程，也无法持续改进规则。

**上下游衔接**：

* 上游接收评估诊断层的诊断报告。
* 下游根据人工结论进入治理候选池、暂未复现池、无需优化归档、规则修正池、埋点缺口池等。

---

#### 3. 实施上线层

**范围**：路径判定 → 设计方案 / 文案发布包 / 平台发布 / 开发排期跟进。

**解决问题**：将“诊断结论”和“优化方向”转化为真实可执行的治理动作。

**相关治理阶段**：改造阶段 / 上线阶段。

**为什么不能缺失**：没有实施上线层，工具只停留在分析，不会产生真实体验改善。

**上下游衔接**：

* 上游承接治理候选池和人工确认结论。
* 下游输出设计方案包、文案发布包、发布记录、开发排期记录和待上线条目。

---

#### 4. 上线与回检准备层

**范围**：上线时间登记 → 上线范围确认 → 埋点口径确认 → 回检就绪检查。

**解决问题**：解决“自动回检前是否具备时间边界和数据口径”的问题。

**相关治理阶段**：上线后准备阶段 / 回检前置阶段。

**为什么不能缺失**：如果缺少实际上线时间、上线范围、上线版本或埋点口径，系统无法判断从哪一天开始回检，也无法保证 API 拉取的数据与本次优化目标一致。

**上下游衔接**：

* 上游承接已发布 / 已上线条目。
* 下游输出已上线待回检池、待补充上线信息池、埋点口径待确认池、数据权限待确认池。

---

#### 5. 回检闭环层

**范围**：自动拉取数据 → 成效判定 → 延长观察 / 复诊 / 归档。

**解决问题**：判断治理是否有效，是否需要延长观察周期，是否需要复诊。

**相关治理阶段**：回检阶段。

**为什么不能缺失**：没有回检，治理无法形成闭环，经验也无法沉淀为可复用规则。

**上下游衔接**：

* 上游承接通过回检就绪检查的已上线待回检条目。
* 下游输出成功案例、踩坑记录、复诊建议、规则修正候选。

---

#### 6. 知识沉淀层

**范围**：成功案例、踩坑记录、规则修正候选、埋点缺口经验沉淀，反哺后续诊断。

**解决问题**：让每次治理结果持续提升后续判断质量，而不是每次从零开始。

**相关治理阶段**：预防 / 评估 / 回检全阶段。

**为什么不能缺失**：知识库是工具长期价值的核心来源，决定 AI 后续分类、评估、建议和成效预估是否越来越准确。

**上下游衔接**：

* 上游接收人工复核结果、回检结果、复诊结果。
* 下游反哺报错特征分类、体验评估标准、实施路径判定、成效预估规则和优化建议生成规则。

## 4. 执行模式

[半自动 + 关键节点人工确认 + 分阶段自动化]

说明：

* **分析链路可自动执行**：报错特征提取、多源数据检索、交叉关联分析、评分计算、报告生成、初步优化方向生成等环节由 AI 自动完成，也支持批量处理。
* **运行控制需自动记录**：每次运行必须记录输入、输出、状态、异常、证据来源、置信度和下游状态，确保可追踪、可复核、可恢复。
* **检索结果透明可复核**：AI 检索到的客户反馈、工单、埋点数据、业务知识和历史案例需在报告中完整呈现，使用者和决策者能判断数据质量和相关性。
* **诊断结果必须进入人工复核**：AI 生成综合诊断报告后，必须生成复核卡，由设计 / 产品 / 运营 / 研发按需确认问题是否准确、是否可复现、是否需要优化、路径是否合理、是否需要补充信息或埋点。
* **路径判定自动建议，执行需人工确认**：
  * 判定为纯文案发布路径后，系统生成文案发布包，人工确认后才允许调用平台发布。
  * 判定为配置化体验路径后，系统生成配置清单，人工确认后才进入配置发布。
  * 判定为前端交互改造路径后，系统生成交互说明和状态规格，人工审核后才进入研发。
  * 判定为后端 / 规则逻辑改造路径后，系统生成规则调整建议，需产品与研发共同确认。
* **上线与回检准备需人工补充关键事实**：
  * 对开发排期条目，需人工提供实际上线时间、上线范围、上线版本、灰度 / 全量状态。
  * 对回检数据依赖埋点的条目，需人工确认埋点文档、埋点版本、事件名称、参数字段和指标口径。
* **回检自动拉取数据，判断需人工介入**：
  * 成效提升 → 自动生成成功案例候选，进入待确认知识库。
  * 无明显成效且样本充足 → 自动生成复诊分析，人工判断是否继续优化。
  * 无明显成效但样本不足 → 自动进入延长观察周期，支持 60 / 90 天二次回检。
* **自动与人工的边界不是“能不能做”，而是“会不会产生外部影响或污染正式知识库”**：
  * 分析、检索、评分、报告生成、复核卡生成、状态标记、问题池分流、回检数据拉取与对比等不产生外部影响的环节，可以自动执行。
  * 文案发布到生产环境、研发排期确认、上线时间确认、埋点口径确认、无成效归因的最终结论、正式知识库沉淀等会产生外部影响或长期影响的环节，必须人工确认。

## 5. 优先原则

### （1）诊断质量优先于覆盖广度

工具的核心价值在于诊断结论的准确性和可操作性，而不是一次能处理多少条报错。

* 支持单条精细诊断，也支持批量评估。
* 批量时通过分批控制质量，确保每条输出的深度不低于人工可复核水平。
* 每个数据源的检索结果必须标注可信度，不强行使用低质量数据做判断。
* 当证据不足时，应降级为“证据不足 / 需人工确认”，不能硬给确定性结论。

---

### （2）最小链路先跑通，再扩展自动化

本工具落地不采用“一次性完整自动化”的方式，而采用：

```text
最小诊断链路 + 轻量运行控制 + 人工复核闭环 + 上线回检准备 + 逐步扩展自动化
```

前期优先保证：

* 诊断准确性
* 证据可追溯
* 人工结论可回写
* 异常条目可分流
* 规则修正可沉淀

中期补齐：

* 优化方案
* 文案发布包
* 开发排期跟进
* 上线登记
* 埋点口径确认

后期再建设：

* 自动回检
* Hook 自动触发
* Cron 定时扫描
* API 数据拉取
* 批量调度
* 月报生成
* 知识库归档控制

---

### （3）闭环完整，但闭环不等于全自动

工具必须覆盖完整的治理闭环，不能只做“分析”不做“验证”：

* 评估诊断 → 人工复核 → 实施上线 → 上线准备 → 回检闭环 → 知识沉淀。
* 每一步的输出是下一步的输入。
* 回检结果必须回流到知识库，形成持续改进的正向飞轮。
* 缺少回检条件的条目不能跳过，必须进入埋点缺口池、待补充上线信息池或埋点口径待确认池。

---

### （4）实施路径显式分流

凡是进入评估诊断的报错，必须明确给出实施路径判定。

实施路径分为四类：

| 路径 | 适用情况 | 主要交付物 |
|------|----------|------------|
| A. 纯文案发布路径 | 只改错误提示文案，不改组件、不改时机、不改逻辑 | 文案发布包 |
| B. 配置化体验路径 | 平台支持配置帮助链接、按钮文案、展示样式、跳转地址 | 配置清单 + 发布包 |
| C. 前端交互改造路径 | 需要改提示形式、出现时机、页面状态、弱打断方式 | 交互说明 + 状态规格 |
| D. 后端 / 规则逻辑改造路径 | 涉及校验规则、接口返回、错误码、业务判断逻辑 | 需求说明 + 规则调整建议 |

不能出现“分析完了但不知道怎么修”的情况；也不能把需要前端或后端改造的问题误判为纯文案发布。

---

### （5）成效预估必须标注可信度

治理成效预估必须标注可信度，不得在证据不足时输出确定性收益结论。

所有成效预估应至少包含：

* 主指标
* 辅助指标
* 预估方向
* 预估区间
* 可信度：高 / 中 / 低
* 依据来源
* 缺失数据
* 不可验证风险
* 后续回检指标

示例：

```text
预计成效：
- 主指标：提交失败率下降
- 预估区间：10% - 20%
- 可信度：中
- 依据：历史同类案例 + 当前报错量稳定
- 限制：缺少任务完成率埋点，无法直接判断转化提升
```

---

### （6）人工复核是规则反哺的入口

人工复核不是流程上的形式确认，而是规则持续优化的入口。

* AI 评估准确 → 进入治理候选池。
* AI 评估基本准确但建议需调整 → 更新当前报告，并沉淀调整原因。
* AI 评估不准确 → 进入规则修正池，生成规则修正候选。
* 条目暂未复现 → 进入暂未复现池，定期观察。
* 条目无需优化 → 进入无需优化归档，作为正常业务拦截样本。
* 需补充信息或埋点 → 进入对应问题池，补齐后重新评估。

---

### （7）自动回检前必须完成上线与埋点口径确认

系统不能默认“条目进入排期”就等于“具备回检条件”。

自动回检前必须确认：

* 实际上线时间
* 上线版本
* 上线范围
* 灰度 / 全量状态
* 优化前基线窗口
* 优化后观察窗口
* 主指标和辅助指标
* 埋点文档路径
* 埋点事件名称
* 埋点参数字段
* API 数据获取方式
* 指标口径是否发生变化

缺少上述关键条件时，不触发自动回检，应进入：

* 待补充上线信息池
* 埋点口径待确认池
* 数据权限待确认池

---

### （8）知识库持续反哺，但正式沉淀需确认

每次优化结果、复核结果和回检结果都应沉淀到知识库，但不能直接污染正式规则库。

建议采用两层知识沉淀：

```text
待确认经验库 → 人工确认 → 正式知识库
```

沉淀内容包括：

* 成功案例
* 踩坑记录
* 规则修正候选
* 埋点缺口经验
* 路径误判案例
* 成效预估偏差案例

---

### （9）与现有治理机制无缝衔接

本工具不是独立系统，而是现有三阶段治理机制中“评估阶段诊断决策”的智能化升级。

* 输入：来自现有数据管道，如去重助手、增量过滤助手、高频过滤助手。
* 输出：纳入现有台账、问题池、月度同步体系。
* 不替代现有规则分类，而是在 `categorize_logic.py` 的基础上做更深层分析。
* 不替代人工决策，而是为决策提供完整的数据支撑和分析依据。

---

### （10）可校验、可追踪、可恢复

工具链路的每一层都要具备可校验性：

* 该环节是否输出了预期格式的结果？
* 该环节的判断是否有明确规则依据？
* 该环节的输出是否被下游正确承接？
* 最终结论是否能追溯到具体证据来源？
* 出错时是否进入正确问题池？
* 人工结论是否成功回写？
* 规则修正是否形成候选记录？
* 回检是否具备上线时间和埋点口径依据？
