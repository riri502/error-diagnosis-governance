## 1. 多源证据类型定义

| 证据类型 | 来源 | 主要作用 |
|---------|------|---------|
| 报错原始信息 | 输入报错表 | 诊断起点 |
| 客户反馈 | 客户投诉、群反馈、邮件、客服记录 | 判断用户真实痛点 |
| 优化工单 | 历史治理单、产品需求、缺陷单 | 判断是否重复问题 / 是否已有方案 |
| 埋点数据 | 报错次数、影响用户数、任务完成率、跳出率 | 判断影响规模与旅程影响 |
| 业务知识库 | 业务规则、操作流程、异常原因解释 | 判断场景和原因是否合理 |
| 设计知识库 | 报错形式、文案、交互、时机规范 | 支撑体验问题判断 |
| 历史案例 | 同类问题治理前后效果 | 支撑成效预估 |

---

## 2. 相关性判定维度（5 维）

| 维度 | 判断问题 |
|------|---------|
| 错误码一致性 | 是否同一个错误码？|
| 场景一致性 | 是否同一个业务模块 / 页面 / 任务？|
| 时间一致性 | 反馈/工单/埋点是否发生在同一时间窗口？|
| 语义一致性 | 反馈描述是否和报错文案 / 报错原因语义一致？|
| 用户影响一致性 | 是否影响同类客户、同类角色、同一旅程节点？|

---

## 3. 相关性等级（4 档）

| 等级 | 判定标准 | 是否可作为核心证据 |
|------|---------|:---:|
| **强相关** | 错误码/页面/业务场景/时间窗口高度一致，且语义匹配 | 可以 |
| **中相关** | 场景一致，但错误码或时间不完全一致 | 辅助证据 |
| **弱相关** | 只在模块、关键词或问题类型上相似 | 仅参考 |
| **不相关** | 业务场景、时间、用户影响均不匹配 | 不使用 |

---

## 4. 多源证据权重

不同证据在不同判断任务中的权重不同：

| 判断任务 | 更重要的证据 |
|---------|------------|
| 判断是否真实影响用户 | 客户反馈、工单、埋点趋势 |
| 判断是否高频 | 埋点数据、报错统计 |
| 判断业务原因 | 业务知识库、错误码、工单 |
| 判断体验问题 | 设计知识库、体验评估标准、页面场景 |
| 判断是否已有治理方案 | 优化工单、历史案例 |
| 判断预计成效 | 历史案例、埋点基线、同类问题回检结果 |

---

## 5. 证据冲突处理规则

| 冲突情况 | 处理方式 |
|---------|---------|
| 报错量高，但无客户反馈 | 标记"高频但用户痛感待确认"，不可直接判高价值 |
| 客户反馈强烈，但报错量低 | 标记"低频高痛点"，需看客户类型和旅程节点 |
| 工单显示已处理，但埋点仍高 | 标记"疑似治理无效/未全量生效"，进入复诊 |
| 知识库说该报错合理，但文案体验差 | 判断"业务拦截合理，但呈现体验可优化" |
| 埋点缺失，但反馈集中 | 可定性判断，但成效预估可信度降低 |
| 多个证据源指向不同原因 | 进入"低置信诊断池"或"需人工确认" |

---

## 6. 证据不足降级规则

| 证据不足情况 | 降级方式 |
|------------|---------|
| 客户反馈源不可用 | 跳过客户影响维度评分，标注"数据不可用" |
| 只有 1 源可用 | 仅输出定性判断，置信度标"低" |
| 所有检索结果均为弱相关或不相关 | 进入低置信诊断池 |
| 关键证据缺失（如无埋点、无知识库）| 在报告中标注限制，进入待补充信息池 |

---

## 7. 输出格式

每条证据统一按以下结构输出：

```text
evidence_id: {ID}
source_type: 客户反馈 / 工单 / 埋点 / 业务知识库 / 设计知识库 / 历史案例
source_name: {具体来源文件或系统}
matched_fields: [{匹配字段1}, {匹配字段2}]
matched_value: {匹配到的具体内容摘要}
matched_time_window: {时间窗口}
relevance_level: 强相关 / 中相关 / 弱相关 / 不相关
confidence: 高 / 中 / 低
summary: {证据摘要，一句话}
supports: [{支撑的结论1}, {支撑的结论2}]
limitations: [{限制说明1}, {限制说明2}]
```
