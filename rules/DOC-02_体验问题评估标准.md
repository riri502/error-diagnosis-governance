## 1. 评估维度总览

| 维度 | 评估什么 | 核心问题 |
|------|---------|---------|
| **时机** | 报错在什么时候触发 | 能不能更早提示？能不能在用户犯错前就阻止？ |
| **形式** | 报错用什么方式呈现 | 弹窗是不是太重了？Toast 是不是太轻了？形式和严重度匹配吗？|
| **文案** | 报错文字的质量 | 用户能看懂吗？知道怎么解决吗？语气让人舒服吗？ |
| **交互** | 报错后的操作路径 | 用户报错后能做什么？有出口吗？能自己解决吗？ |

### 核心理念

**能前置判断的绝不等操作触发，能实时校验的绝不等提交才报错。时机越早，体验越好。**

## 2. 时机评估

### 2.1 时机等级定义（9 级，从早到晚）

| 时机等级 | 触发时机 | 适用报错类型 | 判断条件 | 能否纯前端判断 | 改造优先级 |
|---------|---------|------------|---------|:---:|:---:|
| **时机 1** | 页面加载时 | 权限不足（操作/数据）、数据已锁定/冻结/结账、流程中/处理中、配置缺失、状态不允许操作（按钮预判） | 能否在页面渲染前获取权限/状态元数据 | 否（需后端预查接口） | P0-P2 |
| **时机 2** | 路由进入前 | 页面级权限不足 | 路由守卫能否获取用户权限列表 | 有条件（需权限接口预查） | P0 |
| **时机 3** | 输入时实时 | 格式错误（日期、编码）、长度超限 | 前端能否独立校验格式规则 | 能（纯前端校验） | P0 |
| **时机 4** | 输入框失焦时 | 必填字段为空、单字段数值错误（金额=0）、名称/编码重复（异步查重） | 前端校验字段值是否为空/有效；查重需后端接口 | 部分能 | P0-P1 |
| **时机 5** | 文件选择后 / 上传完成后 | 文件格式不支持、文件过大、文件名不合法、文件内容解析失败 | 前端校验文件属性（格式/大小/名称）；后端解析后返回结果（内容） | 部分能 | P0-P1 |
| **时机 6** | 点击提交时（前端汇总） | 所有字段级校验的最终汇总、跨字段金额勾稽 | 前端汇总所有字段校验结果 | 能（纯前端） | P0-P1 |
| **时机 7** | 提交后（后端返回） | 时间冲突、唯一性冲突（兜底）、状态不允许操作（兜底）、流程中（兜底）、重复操作/已处理、税局交互失败、算税中 | 需后端查询/校验/外部系统返回 | 否 | P0-P2 |
| **时机 8** | 请求拦截层（全局） | 登录失效（401）、网络错误、超时、服务端 5xx、远程调用异常（后台静默） | HTTP 拦截器统一捕获 | 能（前端请求库拦截） | P0-P2 |
| **时机 9** | 页面数据加载返回后 | 数据不存在（列表进入/外部链接进入） | 请求返回空/404 | 否 | P1 |

### 2.2 时机选择原则

```
① 能页面加载时判断 → 绝不等到点击时
② 能输入时实时/失焦判断 → 绝不等到提交时
③ 能前端判断 → 绝不等到后端返回
④ 只有依赖后端/外部数据 → 在返回后轻量反馈
```

### 2.3 时机违规严重度判定

| 严重度 | 判定条件 | 示例 |
|--------|---------|------|
| **严重** | 可以纯前端校验却等到提交后才报错（时机 3/4/5 可覆盖但实际用了时机 7）| 必填为空 → 提交后才弹窗 |
| **一般** | 可以页面加载时判断却等到操作时才报错（时机 1 可覆盖但实际用了时机 7）| 已结账数据 → 每次操作才弹窗 |
| **轻微** | 当前时机已是最佳或接近最佳，仅有微调空间 | 后端唯一性校验 → 已做失焦查重，提交兜底保留 |

## 3. 形式评估

### 3.1 可选形式清单

| 形式 | 适用场景 | 特点 |
|------|---------|------|
| **入口屏蔽** | 用户无权限访问的功能/页面 | 最轻量，用户根本看不到不可用的入口 |
| **按钮置灰 + tooltip** | 当前不可用但原因可前置判断的操作 | 不让用户点下去，tooltip 解释原因 |
| **输入框红字（inline）** | 字段级校验错误 | 紧贴出错位置，所见即所得 |
| **页面警示横幅（banner）** | 持久状态提示（锁定/结账） | 持续展示，不阻断操作 |
| **警示占位** | 数据区域不可用（权限/不存在） | 替代空白页面，给出原因和出口 |
| **全局 Toast** | 轻量通知（终态告知/异步任务进度） | 3-5 秒自动消失，不打断用户 |
| **弹窗** | 阻断性错误（跨字段勾稽/状态不允许/外部系统返回详情） | 最重，保留用于必须用户确认的场景 |

### 3.2 形式决策矩阵

| 报错场景 | 推荐形式 | 判断标准 | 是否保留弹窗 | 优先级 |
|---------|---------|---------|:---:|:---:|
| 操作权限不足 | 入口屏蔽（首选）/ 弹窗（兜底）| 能否在渲染前获取权限 | 兜底时保留 | P0 |
| 数据权限不足 | 警示占位 | 页面可用但数据不可见 | 否 | P1 |
| 登录/会话失效 | 全局 Toast + 静默跳转 | 全局状态变更 | 否 | P0 |
| 网络/超时（页面级）| 警示占位 + 重试按钮 | 页面数据加载失败 | 否 | P0 |
| 网络/超时（操作级）| 全局 Toast（带重试）| 操作提交失败 | 否 | P0 |
| 服务端通用异常 | 全局 Toast | 临时、不可控 | 否 | P1 |
| 远程调用异常 | 全局 Toast | 用户无法干预 | 否 | P2 |
| 参数为空 | 输入框红字（失焦校验）| 字段级问题 | 否 | P0 |
| 格式/长度错误 | 输入框红字 | 字段级问题 | 否 | P1 |
| 唯一性/重复 | 输入框红字（失焦异步校验）| 字段级问题 | 否 | P1 |
| 文件上传校验 | 上传区域红字 | 上传组件级问题 | 否 | P1 |
| 金额勾稽（跨字段）| 弹窗 | 多字段关系，inline 难表达 | **是** | P1 |
| 金额/数值（单字段）| 输入框红字 | 字段级问题 | 否 | P1 |
| 数据不存在（列表进入）| 警示占位 | 用户从列表点击进入 | 否 | P1 |
| 数据不存在（外部链接）| 弹窗 + 返回引导 | 用户从外部链接/直链进入 | **是** | P1 |
| 已处理/重复操作 | 全局 Toast + 自动刷新 | 非错误，是正常终态 | 否 | P0 |
| 状态不允许操作 | 弹窗 | 阻断性错误，需明确解释 | **是** | P0 |
| 流程中/处理中 | 按钮置灰（首选）/ 弹窗（兜底）| 能否前置判断状态 | 兜底时保留 | P1 |
| 已锁定/冻结/结账 | 页面警示横幅 + 编辑置灰 | 持久状态，每次弹窗体验差 | 否 | P1 |
| 考勤配置缺失 | 警示占位 + 设置引导 | 需引导用户去设置 | 否 | P2 |
| 税局/外部交互失败 | 弹窗（含外部原因）| 外部系统反馈，需保留信息 | **是** | P1 |

### 3.3 形式违规严重度判定

| 严重度 | 判定条件 | 示例 |
|--------|---------|------|
| **严重** | 字段级问题用了弹窗（应 inline）、非阻断性通知用了弹窗（应 Toast）、技术裸错误直接透传 | 参数为空弹窗、Network Error 弹窗 |
| **一般** | 持久状态每次操作都弹窗（应 banner）、非错误信息弹窗打断（应 Toast）| 已结账每次弹窗、已处理弹窗 |
| **轻微** | 当前形式可接受但不够轻量，有优化空间 | Toast 可以无提示但保留 Toast 也合理 |

## 4. 文案评估

### 4.1 评估维度

| 维度 | 标准 |
|------|------|
| **完整性** | 是否包含"是什么"（what）+ "为什么"（why）+ "怎么办"（how）三要素？简单错误至少包含"报错描述"+"解决方案" |
| **情绪** | 是否使用指责性/负面词汇？是否包含感叹号（!）等加重语气的标点？语气是否友好？|
| **复杂度** | 是否存在技术术语/开发语言/英文缩写？语句是否通顺简洁？信息层级是否清晰？|
| **引导性** | 是否给出了明确、可执行的下一步操作？是否告知了该联系谁？|
| **准确性** | 描述的错误原因是否与实际场景匹配？字段名是否是用户可理解的 label 而非数据库字段名？|

### 4.2 情绪判定

| 等级 | 判定条件 |
|------|---------|
| **Positive** | 完全没有负面情绪、语气温和、非常友好 |
| **Neutral** | 几乎没有负面情绪、语气适中、较为友好 |
| **Negative** | 有负面情绪、语气强硬、不友好。*触发条件：使用"不准""不允许""非法""失败"等词汇；或使用感叹号 (!) 等加重语气的标点* |

### 4.3 复杂度判定

| 等级 | 判定条件 |
|------|---------|
| **Low** | 无技术术语/开发语言/英文缩写；语句通顺简洁；信息层次分明 |
| **Medium** | 存在少量可容忍的技术术语或英文缩写；语句略显生硬/冗长 |
| **High** | 存在难以理解的技术/业务术语；包含未经解释的开发语言或大量英文缩写；语句严重不通顺或逻辑混乱；大段落堆砌信息 |

*附加规则：若使用了开发语言或难以理解的业务术语 → 至少判为 Medium。若同时语句复杂、包含多个从句 → 判为 High。*

### 4.4 完整性判定

**简单错误**（仅涉及单一错误点、即时可解决）→ 至少包含"报错描述"+"解决方案"。

**复杂错误**（涉及多个错误点、需多步解决、需业务逻辑解释）→ 必须包含"是什么（what）"+"为什么（why）"+"怎么办（how）"三要素。

| 要素 | 定义 | 判定方法 |
|------|------|---------|
| 是什么（what）| 告知发生了什么状况 | 报错文案中是否说明了"出错了/无法操作/发生了XX情况"|
| 为什么（why）| 解释发生的原因 | 报错文案中是否说明了"因为XX原因"（不责怪用户，客观描述）|
| 怎么办（how）| 给出解决方法或建议 | 报错文案中是否说明了"你可以XX"或隐含了操作指引 |

### 4.5 现状问题类型清单

| 问题类型 | 问题描述 | 典型示例 | 建议改进方向 |
|---------|---------|---------|------------|
| **技术裸错误透传** | 英文错误信息、HTTP 状态码直接展示给用户 | Network Error (4822次)、timeout of 120000ms exceeded (1601次)、Request failed with status code 500/502/504、ECONNABORTED (1894次) | 全部包装为用户可理解的中文提示：Network Error→"网络连接异常"；timeout→"处理超时"；5xx→"服务繁忙" |
| **技术术语暴露** | 使用"接口""远程服务""token""签名""参数"等技术术语 | "调用远程服务异常"、"签名已过期，请刷新列表后重新请求"、"参数 token 不能为空！"、"智能记账接口调用异常" | 替换为用户视角的表述：远程服务→"XX 功能"；token/签名→"登录"；参数→"信息" |
| **模糊引导** | "请检查""请刷新"等模糊指令 | "没有该账套的数据权限，请检查"、"公告不存在，请刷新后重试"、"账套不存在，请检查" | 给出具体、可执行的下一步：告诉用户具体联系谁；引导到正确的设置页面；区分"刷新"和"返回列表" |
| **责备语气** | 使用"请勿""不能""不允许"等否定和命令式表达 | "此任务已处理，请勿重复处理。"、"非审批中状态的流程不能撤销!" | 改用中性、正向的表述："该任务已被处理"；"仅审批中的流程可撤销，当前状态为已完成" |
| **字段名不可读** | 报错中直接展示数据库字段名（如 CERTYP、PAMPRJCOD）或技术 ID | "字段[CERTYP:证件类型]的值的长度[3]不能大于定义的最大长度[1]"、"提交数据有误，请检查：成员id不能为空"、"操作失败，错误：PAMPRJCOD 必须设置" | 字段名全部替换为用户可见的 label 名称：CERTYP→"证件类型"；成员 id→"成员"；PAMPRJCOD→"项目编码" |
| **信息缺失** | 报错只说出了问题但没有提供必要的上下文 | "发票金额错误:不含税金额+税额≠ 含税金额"（缺具体数值）；"资产编号已存在"（缺被谁使用）；"当前批次状态不可进行操作"（缺当前状态）| 补充关键上下文：金额不匹配→列出各项具体值；编号重复→展示被占用的记录；状态不符→告知当前状态和允许状态 |
| **文案过长/啰嗦** | Toast 或弹窗文案过长，用户不阅读直接关闭 | "服务异常，可尝试重试解决，若无法解决可联系在线客服，或电话客服400-0695-555"；"您所在企业已开启子公司单独管理模式…请联系[魏来/1022]" | Toast 场景控制在 20 字以内；弹窗场景控制在 3 行以内；详细信息使用折叠方式展示 |

### 4.6 文案违规严重度判定

| 严重度 | 判定条件 |
|--------|---------|
| **严重** | 技术裸错误透传（用户完全看不懂）、字段名不可读（用户不知道说的是什么）、严重信息缺失（报错等于没报）|
| **一般** | 技术术语暴露（能看懂但体验差）、模糊引导（知道有问题但不知道怎么做）、责备语气 |
| **轻微** | 文案略长但信息完整、用词可优化但语义清晰 |

## 5. 交互评估（待补充）

*本节为框架预留。交互维度评估标准需从以下方向展开：*

- [ ] 报错后用户是否有明确的下一步操作？（关闭弹窗后知道去哪/做什么吗？）
- [ ] 报错后是否提供了快捷出口？（重试按钮/联系管理员/返回列表/跳转设置页…）
- [ ] 操作失败后用户数据是否保留？（表单内容是否丢失？）
- [ ] 报错后的兜底路径是否可用？（用户无法自行解决时，能否联系到人？）
- [ ] 是否有防错机制？（能阻止用户进入必错路径吗？）

### 交互违规严重度判定（框架）

| 严重度 | 判定条件 |
|--------|---------|
| **严重** | 报错后无任何出口，用户被困住；操作失败后用户已填写的数据全部丢失 |
| **一般** | 有出口但不明确；兜底路径存在但表述模糊 |
| **轻微** | 出���完整但可进一步优化（如增加快捷入口）|

## 7. 违规严重度判定汇总

| 严重度 | 时机 | 形式 | 文案 | 交互 |
